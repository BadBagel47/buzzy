# Buzzy — framtida ändringar

För övergripande mål se [PLAN.md](PLAN.md), för arbetssätt [WORKING_AGREEMENTS.md](WORKING_AGREEMENTS.md) och för återstart [HANDOFF.md](HANDOFF.md). Tabellen nedan visar aktuell status; äldre avsnitt bevarar historiska beslut.

Nya önskemål får ett eget internt ID och samlas före implementation. Att ett önskemål registreras är inte ett klartecken att implementera det eller ändra det pågående publiceringssteget.

Den här filen är projektets gemensamma lista över funktioner och buggar. Varje rad har en typ:

- **Funktion**: nytt eller ändrat beteende, utseende eller innehåll.
- **Bugg**: något fungerar inte som avsett eller har gått sönder. Ange observerat fel, och skilj på misstänkt och reproducerad orsak.
- **Utredning**: en fråga som behöver besvaras före ett beslut om implementation.

Statusfältet anger det senaste verifierade steget: registrerat → körbesked → ändrat i källan → lokalt prov → publicerat (körning och commit) → användar-/mobilprov godkänt. Återöppna samma ID vid återfall i stället för att skapa ett nytt. Nya rader läggs sist i tabellen Aktuell status. Nytt ID = högsta ID i backloggen (båda tabellerna) + 1. Prioritet: Hög, Medel eller Låg. Parkerade punkter har statusen Parkerad och körs bara när användaren nämner dem.

#387, underlag (förslag, inte beslutat):
- **Nyckeln får aldrig ligga i repot eller i den publika sidan.** Buzzy är en statisk sida på Firebase Spark utan egen server. Alternativ: (1) **egen nyckel i webbläsaren**: hosten klistrar in sin Anthropic-nyckel i Questions; den sparas bara i den webbläsaren och anropen går direkt till Anthropic. Enklast och utan ny infrastruktur, men nyckeln finns i webbläsaren (risk vid XSS) och varje host måste ha egen nyckel. (2) **Cloudflare Worker** (gratisnivå) som håller nyckeln som hemlighet; kräver inloggning eller delad hemlighet så att inte vem som helst kan använda den (hänger ihop med pausade #331). (3) **Frågepaket i förväg** via GitHub Action eller agent, sparade som JSON i repot och importerade i Questions; ingen nyckel i webbläsaren, men inte interaktivt. Agentens rekommendation: börja med (1), lägg (2) som nästa steg om fler hostar ska använda funktionen.
- **Korrekthet i två steg:** (a) generering med Claude Opus 5.5 och webbsökning, med strikt JSON-schema per fråga: fråga, svar, godtagna alternativa svar, kort förklaring, minst en källänk, ämne, svårighetsgrad; (b) separat kontrollanrop som slår upp varje fråga oberoende, underkänner oklara, tvetydiga eller tidskänsliga frågor ("senaste", "nuvarande", rekord) och frågor där källorna inte bekräftar svaret. Bara godkända frågor visas som utkast. Hosten granskar med källor synliga och väljer vilka som läggs i kön; inget läggs till automatiskt. Dubbletter mot befintliga frågor filtreras bort.
- **Ämnen och blandningar:** fritt ämne eller färdiga ämnesknappar, antal, svårighet, språk (svenska/engelska). Blandad omgång via ett "recept", t.ex. 3 geografi + 3 musik 80-tal + 4 sport, med svårighetsfördelning. Recept kan sparas och återanvändas. Frågorna får ämnestagg (synlig i kön) och källa.
- **Placering:** knapp i Questions, bredvid New question, som öppnar en panel med ämne/recept, förhandsgranskning av utkast och "Lägg till valda".
- **Teknik:** Content-Security-Policy behöver tillåta `https://api.anthropic.com` (Hosting-ändring, ingen regeländring). Hostens frågor ligger i `rooms/$code/private`, som bara hosten får läsa och skriva och som inte valideras fältvis, så nya fält kräver ingen regeländring. Leverantören kapslas in så att OpenAI kan läggas till senare.
- **Kostnad:** betalas av den som äger nyckeln (Anthropic API debiteras per användning och kräver ingen prenumeration, bara ett API-konto med saldo). Opus 5.5 kostar 4 USD per miljon inmatningstoken och 20 USD per miljon utmatningstoken, plus en avgift per webbsökning. Uppskattningsvis några kronor per tio kontrollerade frågor; mäts vid första provet.
- Rekommenderad modellnivå för bygget: Opus, eftersom det rör säkerhet (nyckelhantering, CSP) och ett flerstegsflöde mot ett externt API.
