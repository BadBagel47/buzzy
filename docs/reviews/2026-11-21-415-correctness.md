# Buzzy correctness and robustness review

I found 13 defects worth reporting; 8 are confirmed by running against the emulators, the rest by reading. The four that matter most: a host reload during a prepared set silently switches the room to Quick Play, a rejected save retries forever, one "Hidden on viewer" question blanks viewers for the rest of the game, and an interrupted round change bricks the room.

The probes are `probe1.integration.mjs` and `probe2.integration.mjs` in `/tmp/claude-0/-home-user/ab4d401a-d323-5b0a-b9d8-682a3d9753d2/scratchpad/review-correctness/`. ## Findings

### 1. Host reload during a prepared set switches the room to Quick Play and blanks the question — High
- **Where:** `src/bridge.js:364` (restore), `src/bridge.js:52` and `:59` (save).
- **What goes wrong:** In prepared mode `quickQuestion` is `null`, and a `null` in the patch deletes the key in the database. On reload the restore loop is `for(const key of privateKeys)if(key in ui)s[key]=ui[key]`, so the key is skipped and the prototype default `quickQuestion:{id:'quick-initial',…}` stays. `start()` then publishes.
- **Reproduction:** Add a prepared question, switch to Prepared, press Present, reload the host.
- **Evidence (run):** Before reload `quick:null`, presentation text `"First question?"`, source `prepared`. After reload the host has `quickQuestion.id:"quick-initial"`, the presentation is `{"id":"quick-initial","source":"quick","text":""}`, and the player no longer sees the question.
- **Confidence:** Confirmed by running.
- **Fix idea:** On restore assign `s[key]=ui[key]??null` for nullable keys such as `quickQuestion`, or store an explicit `playMode`. Add a test for reload in prepared mode.

### 2. Any rejected save retries forever at about 15 writes per second — High
- **Where:** `src/bridge.js:72-84`; rules in `database.rules.json` for `presentation/image` and `control/correct|incorrect`.
- **What goes wrong:** When `publish()` throws, the saved snapshots are not updated. The `finally` in `operation()` calls `afterRender()` → `scheduleSave()`, which still sees a difference and schedules another save 60 ms later. The loop has no backoff and no stop.
- **Reproduction:** Type a prepared question's image URL as `Https://example.com/a.png` (a phone keyboard capitalises the first letter; `#qimage` is a plain text input). The UI accepts it with `/^https?:\/\//i`; the rule requires `beginsWith('https://')`. Switch to Prepared.
- **Evidence (run):** 19 `PERMISSION_DENIED: Permission denied` toasts in 1.5 s and still growing; Present/Open never succeeds; the header keeps saying "Connected".
- **Other inputs that hit the same loop (by reading):**
  - an image URL with a leading space (the value is saved untrimmed) or longer than 2048 characters;
  - question text over 10 000 characters;
  - points outside ±10 000 (`qpoints` and `room-correct` have no bounds).
- **Confidence:** Confirmed by running (the URL case); the other inputs by reading.
- **Fix idea:** Stop auto-retrying an identical failed payload; map `PERMISSION_DENIED` to a readable message; validate URL, lengths and point ranges in the UI the way the rules do.

### 3. One "Hidden on viewer" question turns the viewer Question setting off permanently — High
- **Where:** `src/bridge.js:15` (`sharedSettings`) and `:111` (`Object.assign(s,value.settings)`).
- **What goes wrong:** The shared value is `settings.viewerQuestion=!!(s.viewerQuestion&&!s.roundViewerHidden)`. `project()` copies that derived `false` back into the host's own `s.viewerQuestion`, which is also a saved private key. Every later question computes `false && …`.
- **Reproduction:** Queue a question with Viewer screen = Hidden on viewer, then a normal one. Present the first, Skip & Next, present the second.
- **Evidence (run):** On the normal question the host has `{"vq":false,"hid":false}` and the viewer has `settings.viewerQuestion:false` with empty text, while the player sees the question.
- **Confidence:** Confirmed by running. `tests/viewer-hidden-351.integration.mjs` only checks the hidden question, not the one after it.
- **Fix idea:** Publish the per-round value under a separate key (for example `viewerQuestionNow`), or do not copy `viewerQuestion` back from settings in `project()`.

### 4. A round change interrupted between its two writes bricks the room — Medium (rare trigger, total impact)
- **Where:** `src/client.js:104-107` (control written first, then `attempts/{r}_{a}`), `src/client.js:116` (`emit` returns while `!values.attempt`), `src/bridge.js:375`.
- **What goes wrong:** If the host tab dies or is reloaded between the two writes of Next/Retry, control points at an attempt that does not exist. No watcher ever emits, and nothing recreates the attempt. The host cannot end the game either, because `confirmExit` requires `networkReady`.
- **Evidence (run):** I advanced control without creating the attempt, then reloaded. Host stayed on "Still connecting. Check your connection or try again." for more than 25 s; the player got "We couldn't reconnect to the room."
- **Confidence:** Confirmed by running, with the interrupted state created by hand.
- **Fix idea:** In host `start()`, create `attempts/{r}_{a}` when it is missing. Better: change the attempt rule to compare against `newData` control and write both in one update.

### 5. A setting toggled while another save is in flight is silently reverted — Medium
- **Where:** `src/bridge.js:78` (`finally` → `project(latest)`), `:82` (`scheduleSave` returns when `busy`), `:111`.
- **What goes wrong:** Switches (`input[data-toggle]`) are not locked while busy; only `[data-action]` and `[data-pick]` elements are. A toggle made during an operation is not scheduled, and the `finally` then overwrites it from the server settings.
- **Evidence (run, 250 ms each-way latency on the host socket):** Clicked Leaderboard off, then Own score off 200 ms later. Result: `leaderboard:false`, `ownScore:true`, and the second switch flipped back to checked.
- **Related, by reading:** A snapshot arriving inside the 60 ms debounce (for example a buzz) reverts an unsaved toggle the same way.
- **Confidence:** Confirmed by running.
- **Fix idea:** Keep a "dirty" set of locally changed setting keys and skip them in `Object.assign(s,value.settings)` until they are published.

### 6. Losing a buzz race shows the player a raw "PERMISSION_DENIED: Permission denied" — Medium
- **Where:** `src/client.js:76` (First Buzz), `:79` (Timed, the `throw e` paths), `src/bridge.js:77`.
- **What goes wrong:** In First Buzz the loser's write is rejected and the error is rethrown: `catch(e){if((await read(`${path}/first`))?.uid!==uid)throw e;}`. The same happens in Timed when a tap lands after the server deadline or after exclusion.
- **Evidence (run):** Two players buzzed at once while both saw phase `open`. The loser got the tip `"PERMISSION_DENIED: Permission denied"`.
- **Confidence:** Confirmed by running.
- **Fix idea:** In `buzz`, when the write is denied and the attempt is taken, closed or expired, return quietly or show "Too late".

### 7. A buzz from a player who is then kicked or banned can never be graded, which blocks Retry — Medium/Low
- **Where:** `canScore` in the frozen prototype line 3307 (`p?.status==='active'`), combined with `src/client.js:95` ("Judge pending buzzes first.").
- **Evidence (run):** Player buzzes, host stops, host kicks the player. Grade buttons go from 1 to 0, and Retry answers `"Judge pending buzzes first."`. The only ways out are Next or re-admitting the player.
- **Confidence:** Confirmed by running.
- **Fix idea:** Skip judgments for non-active players in the retry check, or allow grading or dismissing their buzz.

### 8. The 12 seats are consumed permanently — Medium/Low
- **Where:** rules `members/$uid` (`.write` requires `!data.exists()`) and `seats/$slot` (no delete); `src/client.js:35` ("Room full.").
- **What goes wrong:** Leaving, being kicked or being banned never frees a seat. Every new device or incognito identity takes another one. A banned player can rejoin with fresh identities until the room is full, and the host cannot free seats.
- **Also:** Leavers stay "active", so they keep the preload gate waiting and prevent auto-stop. ARCHITECTURE.md notes the 12-seat limit as provisional and #325 notes that presence is not guaranteed; the permanence and the lock-out are not listed.
- **Confidence:** Confirmed by reading.
- **Fix idea:** Let the owner delete `members`, `seats` and `scores` for a uid, and let a player delete their own on leave.

### 9. "Continue anyway" disables the load gate for the rest of the session — Low
- **Where:** `scripts/generate-ui.mjs:25` (network `beginAutoPreload` returns before `state.preloadBypass=false`); gate at `src/bridge.js:228-231`.
- **What goes wrong:** After one bypass, every later question opens without waiting for players' images, until the host reloads.
- **Confidence:** Confirmed by reading; nothing else resets the flag.
- **Fix idea:** Reset `s.preloadBypass` when the round or `loadKey` changes.

### 10. Decimal points can make grading fail — Low
- **Where:** `src/client.js:87-88` against the judgments rule (`delta == points` exactly).
- **What goes wrong:** The client sends `delta = after - score`. With 0.1 points, the third correct answer computes 0.2+0.1−0.2 = 0.10000000000000003, which does not equal 0.1, so the write is denied. The number inputs accept decimals.
- **Confidence:** Confirmed by reading.
- **Fix idea:** Send the requested points as the delta, or restrict points to integers in both UI and rules.

### 11. Join can fail if the host changes round while it is in progress — Low
- **Where:** `src/client.js:30-36`.
- **What goes wrong:** `c` is read once and reused across all 12 tries; only `presentation/shown` is re-read. If the host skips or advances between the read and the write, `fromRound` never matches the rule and the player sees "Unable to join this room. Check the code with your host." A manual retry works.
- **Confidence:** Plausible.
- **Fix idea:** Re-read control inside the loop.

### 12. Writes have no deadline, so a half-dead socket locks the UI silently — Low
- **Where:** `src/bridge.js:72-78` with `src/client.js` (only `read` is wrapped in `deadline`).
- **What goes wrong:** If the socket is dead but `.info/connected` is still true, `set`/`update` hang. `busy` stays true and all host actions and the player buzzer are disabled with no message until the SDK notices.
- **Confidence:** Plausible.
- **Fix idea:** Show "Still sending…" after a few seconds and trigger `client.reconnect()`.

### 13. AI "Replace rejected" drops the time period — Low
- **Where:** `src/ai-questions.js:264`.
- **What goes wrong:** The replacement items are `{topic,count,difficulty}` with no `period`, so replacements for "Last week" or "80s" questions come back as any-time questions and are stored with `period:'any'`.
- **Confidence:** Confirmed by reading.
- **Fix idea:** Carry `period` from the rejected drafts.

## Checked and found OK
- **Patch chain:** I instrumented every `replace`/`replaceAll` during `generate-ui.mjs`. All 155 targets match. The single miss is a harmless `replaceAll` of `#315de8` on the player page. The base-file hash guard is in place.
- **Timed buzz order:** Three simultaneous buzzes gave `n=3`, orders 1, 2, 3, no errors, and auto-stop to `closed` (run).
- **Control transitions:** Client and rules agree on start, stop, expire, retry, advance, finished and configure. The version check prevents silent overwrites.
- **Scoring:** The no-negative formula in the client matches the rule. Double grading is blocked by `!data.exists()` and "Already judged". Manual adjustments are idempotent per command.
- **Expiry:** A late buzz is rejected by the rules even when the host is offline. `maybeExpire` does not fire while offline, busy or locked.
- **Kick, ban, unban and self-rejoin** match the rules.
- **Host exit:** Delete is guarded against double submit, and players and viewers get the ended state.
- **Viewer:** Registration, `onDisconnect` and re-registration after lost access recover by themselves. Room end is handled.
- **Entry page:** Create is idempotent through the stored command id and deterministic code. A join by an existing member is handled.
- **AI flow:** Model id `claude-opus-5-5`, `web_search_20260209`, the fallback beta with `fallbacks:'default'`, effort, the `pause_turn` loop, the refusal check and the two-source rule are all consistent with current API guidance. Cancel during the top-up keeps the first batch.
