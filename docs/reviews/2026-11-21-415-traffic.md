# Buzzy: traffic, cost and performance review

Read-only review; nothing in `/home/user/buzzy` was changed. I built and ran everything in a scratch copy at `/tmp/claude-0/-home-user/ab4d401a-d323-5b0a-b9d8-682a3d9753d2/scratchpad/review-traffic/` (probe scripts `buzzy-live-pilot/tests/probe.mjs` and `perf.mjs`, logs `probe12b.log` and `perf.log`).

How the numbers were obtained:
- **Database traffic:** emulator runs with real pages (1 host, 4 or 12 players, 1 viewer), counting WebSocket frames per page over CDP. Bytes are JSON payload only, without TLS or framing.
- **Page weight:** plain GETs against https://buzzy.trythis.one. The live asset hashes match my local `build:pilot` output.
- **Runtime:** Chromium with CPU throttling (x4/x6 as a stand-in for a low-end phone). It is headless, so frame rates are indicative only.
- **AI flow:** code reading only; no API calls were made.

Paths are relative to `/home/user/buzzy/buzzy-live-pilot/` unless absolute.

One thing is already right: a healthy, idle room does no reads or writes. Over 100 s with 14 clients I measured 0 writes, 0 reads and 2 one-byte SDK keepalive frames per client. The start page opens 0 connections.

## Findings

### 1. Simultaneous buzzes fight over one counter: 3–5x the writes, and buzzes get lost — High
- **Where:** `src/client.js:74-80` (retry loop at line 77).
- **Measured:** with 12 players buzzing within 0.1–0.9 s, the four rounds where all 12 clicks were sent cost 34, 53, 55 and 58 write frames for 12 buzzes. One player needed 10 attempts.
- **Lost buzzes (measured):** in 2 of 5 rounds buzzes never registered: 1 of 12 in one round and 8 of 12 in another. The players got a toast reading `PERMISSION_DENIED: Permission denied`.
- **Cause:** every timed-mode buzz writes `n+1` plus `hits/uid` to the same attempt node, so only one concurrent writer wins. After a rejection the code re-reads the cached value; if the winner's update has not arrived yet, `after.n<=state.n` rethrows and the buzz is dropped.
- **Further cost:** each retry is another round trip (about 50–150 ms on mobile, estimated), so recorded order can differ from press order.
- **Fix:** write only `attempts/{key}/hits/{uid} = {at: serverTimestamp, cmd}` and derive order by sorting on `at`. That is exactly 12 writes for 12 buzzes, no retries and no lost buzzes. It needs a rules change, since `i == n+1` is validated today.
- **Saving:** about 65–80% of buzz-phase writes and roughly a third of buzz-phase download.

### 2. Connections are never released when a game ends or a tab is left open — High
- **Where:** `src/bridge.js:303-308` (`ended()`), `src/viewer.js:231-234` (`endRoom()`), `src/connection.js:19`.
- **Evidence (code):** only `leave()` (`bridge.js:309`) calls `client.setOnline(false)`. A player on "The host has ended the game" keeps its socket. The viewer stops its listeners after "This game has ended" but also keeps its socket. A hidden tab is never taken offline.
- **Cost:** one of the 100 connections per stale tab, for as long as the browser keeps it alive. One forgotten full room pins up to 17 connections, 17% of the project cap (arithmetic).
- **Fix:** call `setOnline(false)` in `ended()` and `endRoom()`. In `connectionRecovery`, go offline after about 5 minutes hidden and reconnect on `visibilitychange`, which the code already handles. For the host, add an inactivity cut-off, for example 60 minutes with no change to `control`.
- **Saving:** stale connections drop to about zero.

### 3. Rooms are stored forever and two branches have no size limit — High over time
- **Where:** `database.rules.json` (`rooms/$code/private` and `rooms/$code/archive` have a `.write` rule but no `.validate` size limit); `src/client.js:69`; `src/bridge.js:86-90`.
- **Measured:** after 5 rounds with 12 players and 20 AI questions the readable parts of the room were 34 KB: `private` 20.0 KB, `archive` 11.4 KB (about 2.3 KB per round), `members` 1.1 KB.
- **Estimated:** a 20-round full game with 20 AI questions is about 115 KB including `attempts` and `loads`, so 1 GB holds roughly 9,000 abandoned games.
- **Abuse risk:** any anonymous user can create rooms and write arbitrarily large `private` or `archive` values, so the 1 GB cap can be reached deliberately in a handful of writes.
- **Fix:** add size validation on `private/ui` and archive records. Run the scheduled 24 h cleanup proposed in #332. Have the host delete `attempts/{old}` and `loads/{old}` on "next", because the archive already holds the same data.
- **Saving:** storage becomes bounded; per-room size falls by about a third (estimated).

### 4. The player page is 396 KB of HTML that can never be cached — High for phones
- **Where:** `firebase.pilot.json:15-17` (`Cache-Control: no-store`); `scripts/generate-ui.mjs` (inlines the whole prototype).
- **Measured live:** `/player` is 76,202 B brotli, 92,069 B gzip, 396,080 B raw. It contains 221 KB of inline JS and 169 KB of inline CSS. `/host` is nearly identical (76,332 B brotli), so players download the entire host UI.
- **Measured:** a conditional GET with the page's ETag returns 200 with the full body; the same test on an `/assets/` file returns 304.
- **Cold join for one player (measured, brotli):** about 172 KB.

  | Part | Size |
  |---|---|
  | start page | 3.0 KB |
  | Firebase client chunk | 63.3 KB |
  | player HTML | 76.2 KB |
  | bridge JS | 21.2 KB |
  | CSS | 6.1 KB |
  | small chunks | about 2 KB |

- **Per reload or rejoin:** 76 KB every time.
- **Hosting quota (estimated):** a full room is about 2.4 MB cold, so the 10 GB Hosting quota covers roughly 4,000 cold full games a month, the same order as the database quota.
- **Parse cost (estimated):** 221 KB of JS and 169 KB of CSS take about 150–300 ms on a low-end Android before anything runs.
- **Fix, step 1 (one line):** change the HTML to `Cache-Control: no-cache`. Repeat loads should then become 304s, saving about 76 KB per reload; the 304 is expected, not verified.
- **Fix, step 2:** emit the inline script and style as hashed files under `/assets/` (immutable).
- **Fix, step 3:** generate a player page without host-only code and CSS; I estimate that halves it.

### 5. No prompt caching in the AI calls — High (largest AI saving, no quality risk)
- **Where:** `src/ai-questions.js:121-141` (request at 125-132).
- **Evidence (code):** each call runs a server-side web-search loop. Every loop iteration, every `pause_turn` resend (line 138) and the "Call … now" nudge (line 139) re-reads the system prompt, tool schemas and all earlier search results at the full $4/M input price. There is no `cache_control` anywhere.
- **Estimated share:** #412 logged about 64,000 tokens and 10 searches for one run. At $0.01 per search (figure from #414), searches were about $0.10 and tokens about $0.15–0.25, most of it re-read search results.
- **Fix:** add top-level `cache_control: {type: 'ephemeral'}` to the `create` call. Cached prefix reads cost $0.20/M instead of $4/M, and the API adds cache points after server-tool results when caching is on.
- **Saving (estimated):** 50–70% of input-token cost, about $0.05–0.12 per batch of 5.
- **Verify:** `usage.cache_read_input_tokens` should be non-zero. `addUsage` (line 119) already sums the fields but does not keep them apart; log them separately.

### 6. Spare questions are always fact-checked, and a shortfall reruns the whole pipeline — Medium
- **Where:** `src/ai-questions.js:153` (spares), `:175-179` (verify loop), `:214-218` (top-up).
- **Evidence (code):** asking for 5 produces 7, and all 7 are verified with up to 3 searches each (batches of 4 and 3, so up to 21 verifier searches). The spares exist only to replace rejections. If fewer than requested pass, `produce(topUp(...))` runs a second writer call plus verification, and that call adds at least 2 spares of its own.
- **Estimated:** with no rejections, 2 of 7 verifications are wasted, about 29% of verifier cost on a batch of 5 (17% on a batch of 10).
- **Fix:** verify only the requested number first. Verify a spare only when a question is rejected. Call the writer again only when the spares run out.
- **Saving (estimated):** 15–30% of verifier tokens and searches, with the same correctness rule.

### 7. Search count, effort and batch shape in the AI flow — Medium (needs a measured run)
- **Where:** `src/ai-questions.js:129` (`effort:'high'` on both calls), `:63-69` (verifier prompt), `:175` (4 questions per verifier call), `:144` (up to 150 queued questions resent).
- **Fewer searches.** One search usually returns several independent sites. Add a sentence such as "one search often returns several independent sites; stop as soon as two independent sites confirm the answer". Estimated 2–3 searches per question drops to 1–2, saving about $0.01–0.02 and several thousand input tokens per question. The code still enforces the two-host rule (line 189).
- **One question per verifier call, in parallel.** Each question stops paying to re-read the other three questions' search results, and the wall-clock wait roughly halves (estimated).
- **Effort.** Opus 5.5 defaults to `medium`; `high` costs more thinking output at $20/M and more tool calls. Trying `medium` on the writer first, as #414 suggests, is reasonable because the verifier is the safety net.
- **Dedup list.** Send only same-topic questions; this saves up to about 3,000 input tokens per writer call (about $0.012, estimated).
- **Before changing anything.** Store usage per phase (writer vs verifier: input, cache read, output, searches) and show the estimated dollar cost in the panel. Today only totals exist (line 119).
- Model choice stays the owner's decision. For reference, Sonnet 5.5 is $2/$10 and Haiku 5.5 is $0.10/$0.50 per million tokens; the search fee is unchanged.

### 8. Every change to the question queue re-uploads the entire queue — Medium
- **Where:** `src/bridge.js:52` (`privateUi`), `:59` (`changedFields` compares top-level keys only), `:60-71` (`publish`).
- **Measured:** with 20 AI-style questions, flipping one `played` flag sent 19,265 B. `private/ui` was 19.7 KB at 20 questions and 57.7 KB at 60.
- **Cost:** each prepared round sets `played`, so a 60-question quiz uploads about 58 KB per round, about 3.5 MB over the game, from a host who may be on mobile data. It does not count against the download quota, since nobody listens to it, but a host reload downloads it again.
- **Fix:** store questions keyed by id (`private/ui/questions/{id}`) and patch only changed ids.
- **Saving:** about 98% of those bytes.

### 9. Players listen to everyone's "question loaded" status and report it even for spoken questions — Medium
- **Where:** `src/client.js:110,122` (`loads=true` by default; players start a `loads/{key}` listener), `src/bridge.js:173-180` (`preparePlayer` always writes).
- **Measured:** the "next question" step costs about 33 KB of download across a 12-player room, about 2.2 KB per player. Each player's 134-byte `ready` write fans out to the host and all 12 players, and each player also starts 3 new listeners.
- **Evidence (code):** only the host uses the statuses (`bridge.js:147`, `:239`). The host requires them only when the question has an image or visible text.
- **Fix:** pass `{loads:false}` for players. Skip the `ready` write when there is no image and no visible text.
- **Saving (estimated):** about 60% of the "next" download (about 20 KB per round in a full room) and 12 writes per spoken round.

### 10. The viewer tears down and rebuilds all its listeners every round — Low/Medium
- **Where:** `src/viewer.js:235-249` (error handler re-registers), `src/client.js:126-128`, attempts read rule in `database.rules.json`.
- **Measured:** on every "next" the viewer sent an `onDisconnect` update plus 14 listen and 13 unlisten frames (28 frames, about 2 KB up, 3.5–4.7 KB down). Players sent only 3 listens.
- **Likely cause (not confirmed):** read access to `attempts/$key` exists only for the current key. When the round advances, the old listener is revoked, the error reaches the viewer's handler, and the viewer re-registers and re-subscribes to everything.
- **Fix:** treat a revoked old-attempt listener as expected in `watch`, as the comment at `client.js:111-112` intends, so the viewer swaps only the attempt and excluded listeners.
- **Saving:** about 4–6 KB and 25 frames per viewer per round.

### 11. Confetti: 432 elements per burst, up to 1,296, built in one blocking task — Medium on low-end phones
- **Where:** `src/celebration.js:15-23` (432 particles, 17 keyframes each), `:4` (three bursts allowed at once).
- **Measured:**

  | Case | Main thread blocked | Frames |
  |---|---|---|
  | one burst, x1 CPU | 39 ms | 16.7 ms median |
  | one burst, x6 CPU | 177 ms | 50 ms median (about 20 fps), worst 317 ms |
  | three bursts, x6 CPU | 881 ms | 1,296 animated elements |

- Each particle has `will-change: transform, opacity`, so each can become its own compositor layer.
- **Fix:** scale particle count by device, for example 120 on phones (`hardwareConcurrency <= 4` or width under 600 px) and 432 on the viewer. Or draw on a single canvas. Cap phones at one burst.
- **Saving (estimated):** launch time falls roughly in proportion, to about 50 ms at x6.

### 12. Joining opens two connections and initialises Firebase twice — Low/Medium
- **Where:** `src/entry.js:27-36` (connect and join on the start page, then `location.assign('/player')`), `src/bridge.js` (connects again).
- **Measured:** 2 WebSocket connections per join (one after the other). The start page does 6 reads and 1 write; the game page does 2 more reads, 12 listens and 1 write. Database traffic per join is about 2.8 KB up and 3.9–5.9 KB down.
- **Estimated:** the second TLS, WebSocket and auth handshake adds about 0.4–1 s on 4G.
- **Fix:** navigate first (`/player?room=…&name=…`) and join there, or prefetch the game page while the user types.
- **Saving:** one handshake per join.

### 13. Players download host-only code; the SDK chunk can shrink slightly — Low
- **Where:** `src/bridge.js:6-8` (static imports of `ai-questions.js`, `host-theme.js`, `queue-drag.js`; also `host-markup.js`), `src/runtime-config.js` (`getAuth`).
- **Measured:** bridge chunk 67.8 KB raw, 21.2 KB brotli. Client chunk (Firebase app, auth, database) 243.8 KB raw, 63.3 KB brotli.
- **Measured experiment:** `initializeAuth(app,{persistence:browserLocalPersistence})` instead of `getAuth` gives 225.8 KB raw and 58.7 KB brotli (saves 4.6 KB brotli). I built it but did not test that it works.
- **Estimated:** about 45% of the bridge chunk's source is host-only, so `if(isHost) await import(...)` would save players about 9 KB brotli.
- **Fine as is:** the Anthropic SDK is a separate lazy chunk (367 KB raw, 62.6 KB brotli) and is not referenced by any page until a key is used. There are no web fonts and no images.

### 14. Host Questions tab re-renders the whole list on every change — Low/Medium
- **Where:** the `render()` function in the generated host page (from `buzzy-output/buzzy_midnight_studio_v7_51.html`), `src/bridge.js:81-85` (`scheduleSave` stringifies all private state after each render).
- **Measured (median per render):**

  | View | x1 CPU | x4 CPU | DOM nodes |
  |---|---|---|---|
  | Questions tab, 20 questions | 8.7 ms | 39 ms | 1,165 |
  | Questions tab, 60 questions | 25 ms | 120 ms | 3,165 |
  | Play tab, 12 players | 2.6 ms | 9.9 ms | 330 |

- The player view with 11 buzzes takes 14 ms at x6, which is fine. The 150 ms clock interval only updates text, not a re-render (code reading).
- **Fix:** only needed if hosts build long AI queues on phones: render the Questions list incrementally, or skip it when the tab is not shown.

### 15. Forced reconnects on healthy connections — Low
- **Where:** `src/connection.js:19` (returning after more than 15 s hidden forces `goOffline()` then `goOnline()` even when connected), `:21` (any Network Information `change` event does the same), `:10` (retry every 4–30 s forever, which resets the SDK's own backoff).
- **Measured proxy:** a fresh player connection costs about 1.7 KB up, 3.6 KB down, 12 listens and 2 reads.
- **Cost:** a reconnect each time a player returns from another app, during which the buzzer is disabled. On Android, `connection.change` can fire on ordinary signal changes. I did not measure how often.
- **Fix:** on return, reconnect only if `.info/connected` is false or a quick probe fails. Drop or debounce the `connection.change` trigger. Let the retry interval grow beyond 30 s after several failures.

## Capacity on Spark

**The first limit hit is the 100 simultaneous connections.**

- **Simultaneous games:** a full room is 17 connections (1 host, 12 players, 4 viewers), so 5 full rooms fit (85) and a 6th does not. Without viewers a full room is 13, so 7 rooms and 84 players. A typical room of 1 host, 8 players and 1 viewer allows 10 rooms and 80 players. This is arithmetic.
- **Stale tabs lower this:** finding 2 means ended games and forgotten tabs keep their connections.
- **At the cap:** there is no "service full" message. A refused client sees the generic 15 s "Connection is taking too long" error and retries every 4–30 s.
- **Database download (10 GB/month):** a 12-player round costs about 85 KB summed over all 14 clients (measured, including the buzz retries). A 20-round full game is about 1.8 MB of payload, or about 2.3 MB with overhead (estimated), giving roughly 4,300 full games a month. Findings 1 and 9 cut this by about a third.
- **Hosting transfer (10 GB/month):** about 2.4 MB per full game with cold caches and about 1.1 MB with warm caches (from the measured sizes), giving roughly 4,000–9,000 full games a month. With finding 4 fixed, warm games fall to about 0.1 MB.
- **Storage (1 GB):** about 9,000–20,000 abandoned rooms at 50–115 KB each (estimated). It is not urgent, but nothing bounds it and it can be filled deliberately (finding 3).
- **Not verified:** Firebase Auth limits new anonymous accounts per IP address per hour; I recall 100 but did not check. Many first-time devices behind one school or venue network could hit that before anything else.
- **AI cost:** it is paid by the host's own key, so it is not a Spark limit. It is about $0.05 per requested question today (owner's figure: $0.25 for 5). Findings 5–7 together plausibly halve it without touching the two-source rule (estimated; confirm with per-phase usage logging).
